# Resume payload shape (v5)

Stored in `resume_snapshots.payload`. Example: `api/resume-schema.example.json` (generated by running the normalizer; an eval fails if it goes stale).

**Idea:** `inventory` is the career truth. `resume` is a view (what to show + order). Soft remove = drop an id from `resume.includedIds[section]`; do not delete the inventory item.

**V5 adds:** for every experience and project item, a `story` (the person's own words), a `writing` progress marker, and **point** records in `claims[]`. Facts and points gain labels. `item.bullets` becomes a display copy of the points.

**V4 added:** `facts[]`, `claims[]`, `variants{}`.

Older payloads (v2, v3, v4) are upgraded to v5 on read by `api/payload_normalize.py`. Do not write older shapes.

List sections live under `inventory.sections` so built-ins and future custom sections share one shape. Tool calls take `section` + `itemId` (or `section` + `fields` for add), not per-section tool names.

Section field rules (required fields, enrich/polish flags) live in `api/section_registry.py`.

## Top level

| Field | Type | Required | Notes |
|-------|------|----------|-------|
| `schemaVersion` | number | yes | `5` |
| `intake` | object | yes | Intake status + confirmation flags |
| `inventory` | object | yes | Canonical career data |
| `resume` | object | yes | Current resume view |
| `facts` | object[] | yes (`[]` OK) | Atomic statements linked to items. See [Facts](#facts) |
| `claims` | object[] | yes (`[]` OK) | Points and generated claims. See [Claims and points](#claims-and-points) |
| `variants` | object | yes (`{}` OK) | Job-specific views. Parked; nothing new should depend on it |

`intake.status` is `not_started`, `in_progress`, or `complete`. `basicsVerified`
must be true before voice, chat, or list-section tools can run. Skills
confirmation still applies during voice intake.

## `inventory`

| Field | Type | Required |
|-------|------|----------|
| `basics` | object | yes |
| `skills` | string[] | yes (`[]` OK) |
| `sections` | object | yes | Map of section key → `{ title, items }` |

`basics` and flat `skills` are **not** list sections for soft-exclude tools. Basics are **manual-only** (never AI-edited) and must be user-verified.

### `inventory.basics`

| Field | Type | Required |
|-------|------|----------|
| `fullName` | string | yes (required to verify) |
| `email` | string | no |
| `phone` | string | no |
| `location` | string | no |
| `links` | `{ label, url }[]` | yes (`[]` OK; LinkedIn/GitHub are stored here) |

Edit basics with `PATCH /resume/{session_id}/basics`, not AI tools. Verification is `intake.basicsVerified`.

### `inventory.sections[sectionKey]`

| Field | Type | Notes |
|-------|------|-------|
| `title` | string | Display label (e.g. `"Education"`) |
| `items` | object[] | Entries with stable `id`. Array order is document order within the section (`reorder_items`). |

Built-in keys: `experience`, `projects`, `education`, `achievements`. Custom keys may be added later; same bag shape.

### Shared item fields

Most section items include:

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | **Required**, stable (for tools) |
| `status` | `"active"` \| `"archived"` | Default `active` |

Experience/projects may also have `categories[]` and `skills[]` (enrichment). Education stays a credential line (degree, institution, dates) — research/awards belong in other sections.

### Point-bearing items (experience, projects)

Sections whose registry profile has `polishBullets: true` carry points. Their items also have:

| Field | Type | Notes |
|-------|------|-------|
| `story` | object[] | The person's own words for this item. See below |
| `writing` | object | Progress of point writing for this item. See below |
| `bullets` | string[] | **Display copy** of the item's points, in order. Never write it directly |

`story[]` entries:

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | Stable |
| `text` | string | What was said |
| `source` | string | Where it came from. Only `legacy` is written today (a bullet that existed before stories were captured) |
| `at` | string \| null | ISO timestamp; `null` for `legacy` |

`writing`:

| Field | Type | Notes |
|-------|------|-------|
| `status` | string | Only `idle` is written today |
| `questions` | object[] | Open follow-up questions (`[]` today) |
| `followUpsAsked` | number | Count toward the per-item follow-up cap |

## Facts

`facts[]` holds atomic statements. Helpers: `api/facts.py`.

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | Stable |
| `content` | string | The statement |
| `context` | `{ section, itemId, field }` | The item it belongs to |
| `source` | string | e.g. `user` |
| `createdAt` | string | ISO timestamp |
| `kind` | string | `context`, `action`, `tool`, `result`, `scale`, or `unsorted` |
| `owner` | string | `me`, `team`, or `unclear` |
| `quote` | string \| null | Exact words from the story the fact came from |
| `storyId` | string \| null | The `story[]` entry the quote is in |

`add_fact` refuses an unknown `kind` or `owner`. On read, facts missing these labels get defaults without guessing: `kind` is `tool` when `context.field` is `technologies`, otherwise `unsorted`; `owner` is `unclear`; `quote` and `storyId` are `null`.

Today facts are still derived from bullets and technologies (`sync_facts_from_item`). `quote` and `storyId` stay `null` until facts are extracted from stories.

## Claims and points

`claims[]` holds two kinds of record. Helpers: `api/claims.py`.

- A **point** has an `itemId`. It is one bullet of one item.
- A **generated claim** has no `itemId` (created by the parked job-analysis flow; may carry `variantId`).

Point fields:

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | Stable. Kept while the text is unchanged |
| `content` | string | The point text |
| `supportedBy` | string[] | Fact ids backing it (`[]` until checked) |
| `section` | string | Section key of its item |
| `itemId` | string | Its item |
| `order` | number | Position within the item, from 0 |
| `status` | string | `unchecked`, `supported`, `needs_review`, or `user_edited` |
| `issues` | array | Problems found with it (`[]` OK) |
| `origin` | string | `legacy`, `ai`, `user`, or `imported` |

`new_point` refuses an unknown `status` or `origin`. Points written by the existing add/update/enrich paths are `legacy` and `unchecked`.

### Points are the source; `bullets` is a copy

- Change an item's points only through `set_item_points(payload, section, item_id, texts)`. It keeps the id and labels of any point whose text is unchanged, creates points for new text, drops the rest, and refreshes that item's `bullets`.
- `rebuild_bullets` is the only code that writes `item.bullets`.
- Blank or non-string texts are dropped.

## `resume` (view)

| Field | Type | Required | Notes |
|-------|------|----------|-------|
| `title` | string | yes | e.g. "General Resume" |
| `summary` | string | no | Per-resume blurb |
| `includedIds` | object | yes | Map `sectionKey` → `string[]` of item ids (kept in inventory item order after `reorder_items`) |
| `sectionOrder` | string[] | yes | Order of section keys on this resume (`reorder_sections`) |

Example: `includedIds.projects = ["proj_music"]`. Soft hide = remove that id from the list for that section. Preview item order follows `inventory.sections[section].items`.

## Soft vs hard removal

| Intent | Action |
|--------|--------|
| Hide from this resume | Remove id from `resume.includedIds[section]` |
| Keep but retire | Set `status: "archived"` and exclude from view |
| Truly erase | Rare; separate hard-delete tool later |

## Normalizing on read

`normalize_payload` runs on every read and before every save. It is safe to run repeatedly.

| Incoming payload | What happens to points |
|------------------|------------------------|
| v2, v3, v4 (includes PDF imports and old undo/version snapshots) | Points are built from each item's `bullets`; each bullet also becomes a `legacy` story entry |
| v5 | `bullets` is rebuilt from the points |
| v5 item with `bullets` but no points | The item adopts its `bullets` as points |

Ids created during an upgrade are derived from the item id and text, so the same payload always upgrades to the same result.

Older payloads used top-level `inventory.experience` / `projects` / … arrays and camelCase `includedExperienceIds`, `includedProjectIds`, etc. Those are converted to `sections` + `includedIds` first.

## Saving

All writes to `resume_snapshots.payload` go through two functions in `api/main.py`:

| Function | Use |
|----------|-----|
| `_save_payload` | Change an existing resume. Normalizes, keeps an undo copy, bumps `version`, records a `career_versions` entry with a summary |
| `_create_snapshot` | Create a resume. Normalizes and records the first `career_versions` entry |

Do not write the table from anywhere else; the `single_save_door` eval fails if code does.

## Intake

- **Voice cold start** creates a blank **v5** record. **PDF import** builds a v3-shaped record that is upgraded to **v5** before it is saved.
- First resume view usually includes all `active` item ids per section.
- Voice/PDF content editing waits until `intake.basicsVerified` is true.

## Out of scope here

- Multi-resume rows in DB (one resume per account)
