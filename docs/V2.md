# Resume Builder → AI Career Intelligence Project

We are changing the direction of this project.

This is **not being built as a startup or SaaS resume builder**. Do not optimize for subscriptions, marketing features, dozens of templates, ATS gimmicks, or competing with existing resume builders.

The goal is to turn the existing application into a technically strong **AI engineering project**.

The central question this project should explore is:

> How can an AI system reliably transform unstructured user input into persistent structured career data, retrieve relevant evidence from that data, generate resume content without inventing information, and verify that generated claims are actually supported?

The resume itself is an output of the system.

The core system is a **structured, versioned career knowledge base with AI-powered retrieval and grounded generation**.

# The Core Architecture

The system should have a canonical source of truth representing a user's career.

Conceptually:

```text
Canonical Career Knowledge
│
├── Experiences
│   ├── Company
│   ├── Role
│   ├── Dates
│   ├── Responsibilities
│   ├── Projects
│   ├── Skills / Technologies
│   └── Achievements
│
├── Independent Projects
├── Education
├── Skills
├── Achievements
└── Supporting Facts / Evidence
```

This structured career data is the primary source of truth.

A resume should not simply be an independent blob of text.

Instead:

```text
Canonical Career Knowledge
          │
          ▼
   Resume Content Selection
          │
          ▼
     Resume Variant
          │
          ▼
     Resume Renderer
          │
          ▼
       Final Resume
```

There must be a clear separation between:

```text
Career Facts
     ≠
Resume Variant / Content
     ≠
Visual Template
```

Changing a resume variant should not silently corrupt or overwrite canonical career facts.

# The Five Core AI Problems

The project should focus on these five capabilities.

Do not add AI technologies that do not directly support one of these problems.

---

## 1. Natural Language → Structured State

The user should be able to type or speak naturally.

Example:

> Add Redis to my ChaiShots recommendation work and mention that I reduced latency to under 200ms.

The system should transform this into a structured operation.

Conceptually:

```text
User Input
     ↓
LLM Understanding
     ↓
Structured Operation
     ↓
Entity Resolution
     ↓
Validation
     ↓
Deterministic Database Mutation
```

Example output:

```json
{
  "operations": [
    {
      "type": "UPDATE",
      "target": {
        "entityType": "project",
        "entityId": "..."
      },
      "changes": {
        "technologies": {
          "add": ["Redis"]
        }
      }
    },
    {
      "type": "ADD",
      "target": {
        "entityType": "achievement",
        "parentEntityId": "..."
      },
      "data": {
        "text": "Reduced recommendation latency to under 200ms"
      }
    }
  ]
}
```

The exact schema can differ.

However, follow this architectural principle:

> The LLM proposes structured operations. Deterministic application code validates and executes them.

Do not allow an LLM to directly perform arbitrary database mutations.

The system should support a minimal, explicit operation set such as:

```text
ADD
UPDATE
DELETE
REORDER
MOVE
RESTORE
```

Use stable internal IDs wherever possible.

---

## 2. Entity Resolution and Ambiguity

The system must not blindly guess what the user means.

Example:

> Remove my old internship.

If there are multiple possible internships, the system should not randomly select one.

Instead:

```text
User Request
      ↓
Candidate Entity Retrieval
      ↓
Candidate Ranking / Resolution
      ↓
┌─────────────────────────────┐
│ 0 matches → Ask / fail      │
│ 1 match  → Continue         │
│ Multiple plausible matches  │
│          → Clarify          │
└─────────────────────────────┘
```

Example clarification:

```text
I found two internships that may match:

1. HyreFox — AI Tech Intern
2. ChaiShots — AI Tech Intern

Which one do you mean?
```

Do not build a complicated "multi-agent ambiguity agent."

First determine how much of this can be solved deterministically through candidate retrieval and validation, with the LLM only helping when semantic interpretation is genuinely needed.

The system should prefer:

> Ask when uncertain rather than confidently making an unsupported change.

---

## 3. Semantic Retrieval Over Career Evidence

We should investigate whether semantic retrieval is actually useful.

Do not add a vector database just to claim that this project uses RAG.

The structured database should handle queries such as:

> Show my ChaiShots projects.

However, semantic retrieval may be useful for questions such as:

> What have I done that demonstrates backend engineering?

or:

> What experience do I have that relates to distributed systems, scalability, or performance?

Relevant evidence may exist across multiple experiences without using those exact words.

For example:

```text
Query:
"What demonstrates distributed systems experience?"

Possible relevant evidence:

- Event-driven workflows using SQS
- AWS Lambda infrastructure
- Redis caching
- Asynchronous processing
```

Investigate a retrieval architecture such as:

```text
User Query
     │
     ├── Structured Retrieval
     │
     └── Semantic Retrieval
               │
               ▼
        Candidate Evidence
               │
               ▼
           Reranking
               │
               ▼
        Relevant Evidence Set
```

However:

* Start simple.
* Establish a retrieval baseline.
* Only add embeddings/vector search if semantic queries actually require it.
* Evaluate retrieval quality instead of assuming RAG works.

If semantic retrieval is introduced, clearly document why structured queries alone were insufficient.

---

## 4. Evidence-Grounded Resume Generation

This is one of the most important capabilities.

The system should distinguish between:

### Career Facts

```text
Used Redis for caching.

Built AWS Lambda functions.

Implemented SQS workflows.

Reduced recommendation latency to under 200ms.
```

and:

### Generated Resume Content

```text
Built an event-driven recommendation pipeline using AWS Lambda,
SQS, and Redis, achieving sub-200ms response latency.
```

The generated statement is not itself the source of truth.

It should be linked to the facts that support it.

Conceptually:

```text
Career Facts
     │
     ▼
Relevant Evidence Retrieval
     │
     ▼
LLM Generation
     │
     ▼
Generated Resume Claim
     │
     ├── Fact A
     ├── Fact B
     ├── Fact C
     └── Fact D
```

The data model should support provenance.

At minimum, we should be able to answer:

> Why is this statement on my resume?

The answer should identify the source facts that were used.

Do not over-engineer a full knowledge graph immediately.

Implement the minimum data model required to trace generated claims back to supporting evidence.

---

## 5. Claim Verification

The system should not blindly trust its own generated content.

We want to investigate a verification pipeline.

Conceptually:

```text
Generated Resume Content
          ↓
Extract Atomic Claims
          ↓
Retrieve Supporting Evidence
          ↓
Verify Support
          ↓
┌─────────────────────────┐
│ Supported               │
│ Partially Supported     │
│ Unsupported             │
└─────────────────────────┘
```

Example:

Generated claim:

> Designed scalable distributed systems serving millions of users.

Available evidence:

```text
Used AWS Lambda.
Implemented SQS workflows.
Used Redis.
```

Expected result:

```text
Unsupported or insufficiently supported.
```

The system should either:

1. Reject the claim.
2. Flag it for user review.
3. Rewrite it into something the evidence supports.

Do not assume an LLM verifier is automatically correct.

If using an LLM for verification, treat it as another probabilistic component and evaluate it.

# Data Model: Facts vs Presentation

Please investigate introducing a clear distinction between:

```text
Canonical Fact
```

and:

```text
Derived Resume Claim
```

Example:

```text
FACT

id: fact_123

content:
"Implemented Redis caching for recommendation workflows."

context:
ChaiShots → Personalization Project

source:
User-provided information

──────────────────────

DERIVED CLAIM

id: claim_456

content:
"Built a Redis-backed recommendation system."

supportedBy:
[fact_123, fact_124]
```

The exact schema is flexible.

The important principle is:

> Facts are persistent source data. Resume claims are derived representations.

This distinction should make versioning, grounding, and verification easier.

# Versioning

All meaningful changes to canonical career data should be recoverable.

We need a sensible versioning strategy.

Please evaluate:

1. Full snapshots.
2. Operation/event log.
3. Snapshot + operation log.
4. Structured JSON patches.

Choose the simplest architecture that supports:

```text
View history
Undo
Restore
Compare versions
```

Do not implement Git unnecessarily.

Do not introduce event sourcing purely because it sounds sophisticated.

Explain the tradeoff and recommend an approach appropriate for this project's complexity.

# Resume Variants

The canonical career profile should remain independent from job-specific resumes.

Conceptually:

```text
Canonical Career Knowledge
        │
        ├── AI Engineer Resume
        │
        ├── Backend Engineer Resume
        │
        └── Job-Specific Resume
```

A variant can:

* select different experiences
* reorder content
* emphasize different evidence
* include/exclude projects
* generate different grounded descriptions

However:

> A resume variant must not silently change the canonical career facts.

# Job Description Analysis

A user should be able to provide a job description.

The system should convert it into a structured representation.

Conceptually:

```text
Job Description
       ↓
Requirement Extraction
       ↓
Normalized Requirements
       ↓
Career Evidence Retrieval
       ↓
Evidence Assessment
       ↓
Resume Composition
```

For each requirement, distinguish between:

```text
DIRECT EVIDENCE
PARTIAL / TRANSFERABLE EVIDENCE
NO EVIDENCE
```

Example:

```text
Requirement:
Kubernetes

Career Evidence:
Docker
AWS Lambda

Result:
No direct Kubernetes evidence.
Related infrastructure experience exists,
but the system should not claim Kubernetes experience.
```

Avoid meaningless "82% match" scores unless we can define and justify exactly how they are calculated.

The system should prefer transparent evidence-based reasoning.


# Explicitly Avoid These Anti-Patterns

Do not add any of the following unless a concrete problem justifies them:

* Multi-agent systems for simple workflows.
* LangGraph purely for orchestration.
* A vector database for all application data.
* RAG where structured database queries are sufficient.
* Autonomous agents where a deterministic workflow is safer.
* LLM calls for deterministic business logic.
* Fake ATS scores.
* Arbitrary confidential document ingestion.
* Complex architecture that cannot be explained or evaluated.

The goal is not AI buzzword coverage.

The goal is to demonstrate good engineering judgment.
